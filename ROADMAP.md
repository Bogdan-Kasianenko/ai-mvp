# Caro — план на октябрь (demo → pilot)

Работаем по этапам. Следующий этап начинается после проверки результата предыдущего.
Поиск компании для пилота можно вести параллельно с техническими задачами.

## 1. Основа демо

- [x] Проверить текущую архитектуру: Express backend и OpenAI API уже подключены.
- [x] Убедиться, что ключ не находится во frontend и `.env` исключён из Git.
- [x] Отключить хранение ответа через `store: false`; честно описать передачу
      сообщений OpenAI и текущее отсутствие истории на сервере.
- [x] Обновить инструкцию запуска и описание текущих возможностей.
- [ ] Проверить ошибки API: отсутствие ключа, лимит/429, недоступность сервиса,
      таймаут и некорректный ответ.
- [ ] Проверить весь сценарий чата на desktop и mobile; исправить найденные
      визуальные и функциональные ошибки.
- [ ] Перед публичным доступом ограничить частоту запросов к платному API.

Готово, когда демо устойчиво работает на телефоне и компьютере, а ошибка AI
показывается понятным сообщением без потери возможности продолжить чат.

## 2. Знания компании и поведение AI

- [ ] Заполнить тестовые сведения: услуги, адрес/контакты, часы работы, способы
      записи, FAQ, известные цены и услуги, которые компания не оказывает.
- [ ] Обновить инструкции: короткие ответы, обращение на «Вы», язык
      пользователя, уточнения вместо выдуманных цен, отсутствие окончательной
      диагностики и обещаний безопасности движения.
- [ ] Проверить не менее 20 типовых и сложных вопросов, записать плохие ответы,
      исправить инструкции и повторить проверку.

Готово, когда AI отвечает только по известным данным и корректно уточняет
неизвестное.

## 3. Память диалога

- [ ] Ввести ID разговора и выбранный способ временного хранения.
- [ ] Передавать предыдущие сообщения с ограничением длины истории.
- [ ] Проверить диалог из 10–15 сообщений, перезагрузку страницы и срок жизни
      разговора.
- [ ] Задокументировать, когда история удаляется.

Готово, когда AI помнит ранее описанные автомобиль и симптомы, не спрашивая
одно и то же повторно.

## 4. Заявка на обслуживание

- [ ] До сбора контактов подготовить понятное уведомление о данных и способ
      связи с человеком.
- [ ] Постепенно собирать только нужные сведения об автомобиле, проблеме и
      удобном времени; не требовать все поля сразу.
- [ ] Отдельно вести структурированное состояние разговора.
- [ ] Создавать одну заявку с ID, временем, статусом и ссылкой на разговор;
      подтвердить её создание клиенту.
- [ ] Проверить сохранение, отсутствие дублей и обработку опасных симптомов.

Готово, когда сотрудник получает понятную заявку и данные сохраняются
предсказуемо.

## 5. Первый пилот и измерение результата

- [ ] Найти сервис, согласный протестировать продукт на реальных данных.
- [ ] Проверить знания компании, доступ, уведомления о данных и работу виджета.
- [ ] Провести тестовые разговоры и исправить критичные ошибки перед запуском.
- [ ] Измерять разговоры, заявки, неудачные ответы и отзыв владельца.
- [ ] Выбрать следующий модуль по результатам пилота.

Курс и улучшение Codex workflow идут параллельно, если не задерживают демо
и первый пилот.
